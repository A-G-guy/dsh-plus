# 本机部署与重启

## 生产拓扑（现状，勿在开发流程中改动）

| 组件 | 管理 | 监听 | 说明 |
|---|---|---|---|
| `dsh-web.service` | systemctl（system，User=agguy） | 127.0.0.1:3080 | `dsh web --trusted-host miniserver.tail27b689.ts.net`，`Restart=always` |
| `dsh-proxy.service` | systemctl | 127.0.0.1:3081 | `~/.dsh/proxy.mjs` 回环重写代理 + 弱网增强 |
| tailscale serve | `ExecStartPost` 内 `--bg` 持久映射 | tailnet https:3080 | https:3080 → proxy:3081 → dsh:3080 |

要点：tailscale serve 的映射是持久配置（`--bg`），dsh-web 重启后无需重配；
dsh-proxy 与插件无关，插件变更只需重启 dsh-web。

### 弱网增强

反代源文件在仓库 `deploy/dsh-proxy.mjs`，部署副本为 `~/.dsh/proxy.mjs`
（改仓库副本后 `cp` 过去并 `systemctl restart dsh-proxy` 生效；不影响 dsh-web）。
三项均为纯 HTTP 语义，不解释 dsh 内部格式，因此不随官方更新调整：

1. `/plugins/*`（combo 插件包，排除 SSE `/plugins/events`）：向 dsh 请求 identity
   并完整缓冲，取齐后带 `Content-Length` 一次发出；上游截断则在本地重试
   （≤3 次，退避 50/150ms）。客户端可感知总长与截断，弱网下不出现半截 JS；
   随后按 `Accept-Encoding` 重新压缩为 brotli(q5) / gzip。
2. `/assets/` 下**文件名自带内容哈希**的构建产物 → 补 `immutable`。
   哈希由上游构建按内容生成、引用它们的 index.html 每次现场渲染，内容一变文件名
   即变，结构上不可能陈旧；`favicon.svg` / `manifest.webmanifest` 不带哈希，
   不在规则内。
3. `text/html`（index 与 token 页）→ 补 `no-store`（防浏览器启发式缓存启动图）。

明确不做：不缓存响应体、不改写 URL/rev、不触碰 `/api`（RPC）与 SSE。

引入背景（半截插件包与旧启动图问题、压缩收益实测）见
[事故记录](../repo/事故记录.md)。

配套插件 `@dsh-plus/boot-retry` 补「手机↔服务器」这一段（反代之上的 TCP 层，
反代无从感知）：经官方 `__DSH_TRANSPORT__.loadBundle` 缝注入零缓存重试加载器。
详见 `packages/boot-retry/docs/README.md`。

排查边界：插件包 URL 本身已由官方按内容哈希寻址（`rev = sha1(脚本+sourcemap)`，
且带 `immutable`），**文件不改则重启后 URL 不变**——若观察到重启后仍全量重下，
先查反代是否吞掉了 `cache-control` 或改写了 URL，而不是怀疑 dsh。


### 访问围栏（@dsh-plus/access-gate，已合并官方认证）

- 唯一凭据 = 官方 browser-auth cookie（启动令牌交换，30 天，按 host:port 分别持有）；
  access-gate 不再持有自有令牌，只补官方不覆盖的面（静态资产、插件自有路由）
  并提供可选 IP 附加围栏与 IP 信任自动登录。
- **登录（默认）**：未认证的浏览器导航自动渲染 token 输入页（PWA 内同样可用——
  粘贴一次启动令牌即恢复 PWA）；当前认证链接经 `dshctl url` 获取（含 tailscale
  变体：`--host miniserver.tail27b689.ts.net:3080 --scheme https`）。
- **登录（IP 信任自动登录，已启用）**：`autoLoginTrustedIps=true` 时白名单
  （`allowedIps`，覆盖 tailnet 内全部设备的 v4+v6）来源未认证即自动铸造官方
  cookie，免输 token；cookie 到期后任一访问自动重签。白名单外仍走 token 页。
- **配置**：webui 设置 → 插件 → 可配置 →「访问控制」卡片（热生效，即时可逆）。
- **远程全锁自救**：ssh 隧道到本机后直连 `127.0.0.1:3080`（loopback 在 gate 层
  永久放行），经 `/dsh-plus/gate/launch-url` 取当前令牌完成官方登录后改配置。
- 启动令牌随每次 dsh-web 重启更新；cookie 不失效则无需重新登录（跨重启有效）；
  autoLogin 开启时连 token 也无需（见上）。

## 开发拓扑（dshctl 管理，与生产零共享）

| 组件 | 监听 | 说明 |
|---|---|---|
| mock-llm | 127.0.0.1:3917 | `scripts/mock_llm.py`，dev 实例唯一模型后端 |
| dsh-web-dev | 127.0.0.1:3082 | `DSH_HOME=~/.dsh-dev dsh web --port 3082` |

- 隔离手段：独立 `DSH_HOME`（~/.dsh-dev）、独立端口、独立进程组（pidfile/log 在
  `~/.dsh-dev/run/`）、模型接线只指向 mock（dev profile 的 `cordis.patch.yml` 行级
  覆盖，`doctor` 常驻检查）、真实密钥环境变量启动时被覆盖为 dummy。
- dev 实例默认脚本后台管理，不注册 systemctl、不接 tailscale。模板
  `deploy/dsh-web-dev.service.example` 仅供需要常驻时参考，默认不启用。
- 端口规划：3080/3081 生产占用，dev 用 3082、mock 用 3917；冲突时 `doctor` 会报。

## 生产安装与重启流程

```bash
python3 scripts/dshctl.py install-prod <包>     # pack 闭包 → vendor 进 profile → dump-config 验证
python3 scripts/dshctl.py restart-prod          # 交互确认后 sudo systemctl restart dsh-web
```

`dshctl finish` 的第 6 步复用同一安装机制（目标包 ∪ 本次发布包，`--no-install` 可跳过），
但**重启永远不在收尾链路内**——finish 结束后按需确认执行 `restart-prod`。

安装机制（脚本封装，勿手工改 profile）：私有包不在 registry，`install-prod` 把目标包及其
`workspace:*` 传递闭包全部 pack 成 tarball，复制到 `~/.dsh/profiles/web/vendor/dsh-plus/`，
并在 profile `package.json` 的 `dependencies` 与 `pnpm.overrides` 双写 `file:` spec
（overrides 是让传递依赖解析到本地 tarball 的关键），最后 `dsh plugin install` + 组合树验证。
安装只改文件、不动运行中的服务，重启后才生效。`install-prod --dry-run` 可只读预览闭包、
依赖图与将写入的 spec。

平台单实例守卫（事故沉淀，详见 [adr/0001](../repo/adr/0001-平台依赖必须-peer.md)）：

- 安装前：闭包内任何包把平台包（`@deepseek-ai/*`、`@earendil-works/pi-ai`）声明为
  运行时依赖 → 直接拒绝；安装后：profile 顶层检出平台包实体副本 → 直接失败。
- profile 布局：`pnpm-workspace.yaml` 保持 dsh 模板默认 `nodeLinker: hoisted` +
  `autoInstallPeers: false`（hoisted 让遮蔽提升至顶层、可被 doctor 检出；isolated 会把
  副本藏进 .pnpm 逃过扫描，已弃用。真正防线是 peer 化 + 安装守卫）。
- `dshctl doctor` 常驻"无平台包顶层遮蔽 + 布局"两项检查；`dshctl smoke-prod` 是
  scratch home 的等价回归（不碰生产，零费用），改依赖声明或 dsh 平台升级后必跑。

防陈旧（同版本号重复 install 也必然刷新）：

- vendor 内文件名追加 tarball 内容哈希：`slug-version-<sha256前8位>.tgz`，内容变则
  `file:` spec 字符串变，pnpm 必然重新解析——根治"同版本号、同文件名不刷新 node_modules"。
- 同包旧 vendor tarball 自动清理；安装后逐文件比对 tarball 与 node_modules 内容哈希，
  不一致直接失败并列出差异文件（重跑 `install-prod` 即可）。

重启影响与保障（restart-prod 会在确认前再次提示）：

- 正在使用的 Web GUI（包括可能正在执行本操作的会话）中断数秒；会话持久化于
  `~/.dsh/sessions`，重启后可恢复。
- `Restart=always` + `RestartSec=3` 自动拉起；`restart-prod` 重启后自动校验 `is-active`。
- 建议在无重要会话运行时重启；若 GUI 起不来，`journalctl -u dsh-web -n 100` 排查。

## 回滚

```bash
python3 scripts/dshctl.py uninstall-prod <包>   # 移除依赖/overrides/bundle 登记并重装
python3 scripts/dshctl.py restart-prod
```

生产只装 vendor 里的版本化 tarball，回滚是确定性的；编排层问题也可编辑
`~/.dsh/profiles/web/cordis.patch.yml`（用户层，优先级最高）覆盖或禁用对应行。

## 常见故障

| 症状 | 排查 |
|---|---|
| dev 起不来 | `~/.dsh-dev/run/dsh-web-dev.log`；`dshctl dev status` |
| 模型无响应/报鉴权 | 确认打到 mock：`~/.dsh-dev/run/mock-llm.log` 应有请求记录；若没有，说明 dev 配置泄漏了真实 provider，立即停止并检查 `~/.dsh-dev/profiles/web/cordis.patch.yml` |
| 插件行没生效 | `DSH_HOME=~/.dsh-dev dsh --profile web --dump-config` 看组合树 |
| install 后插件未更新 | 安装校验器会直接报错并列出差异文件；重跑 `install-prod`（哈希 spec 机制保证 pnpm 刷新） |
| 生产重启后异常 | `journalctl -u dsh-web`；回滚流程见上 |
| 工具调用报 `Cannot read properties of undefined (reading 'prepare')` | 平台包顶层遮蔽复发：`dshctl doctor` 的遮蔽检查定位带入副本的包，把其平台依赖改 peer 后重装；详见 [adr/0001](../repo/adr/0001-平台依赖必须-peer.md) |
| 插件加载失败（如官方平台破坏性更新） | `@dsh-plus/lifeboat` 会自动隔离失败的 dsh-plus 插件并告警（journal 落 `$DSH_HOME/dsh-plus/lifeboat/state.json`）；手动路径：向 `~/.dsh/profiles/web/cordis.patch.yml` 追加 `- id: <条目id>` + `disabled: true`，或 `dsh plugin --profile web remove <pkg>` 整个卸载 |

### 配置文件所有权（重要）

运行中的 dsh 实例会把 settings 写入 profile 的 `cordis.patch.yml`（行级覆盖层）。
实例存活期间手动编辑
`cordis.patch.yml` 可能被回写覆盖——settings 写入按内存中的活动配置整值序列化
（现象与案例见 [事故记录](../repo/事故记录.md)）。
手动编辑纪律：**先停实例，再编辑，再启动**；改完立即 `/reload` 让内存与磁盘对齐也可。

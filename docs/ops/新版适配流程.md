# 新版本 dsh 适配流程（runbook）

dsh 新版发布后的升级适配标准流程；铁律由历史事故沉淀而来（见
[事故记录](../repo/事故记录.md)）。平台依赖一律走 registry（`dshctl platform-sync <版本>`
核验并统一钉版），不自行构建平台包；官方机制现状见
[官方机制参照](../reference/官方机制参照.md)，本仓只支持已验证基线
（当前 `0.2.1-alpha.2`，见[仓库管理规范](../repo/仓库管理规范.md)）。

## 铁律

1. **隔离环境**：新版构建/验证全程使用独立 `DSH_HOME`（如 `/tmp/dsh-alpha-scratch`）、
   独立端口、独立进程；适配完成前绝不动生产 profile 与运行中实例。
2. **飞行中不换骨**：运行中实例依赖的 profile 符号链接池
   （`~/.dsh/profiles/node_modules` → 全局安装）与 vendor tarball，绝不原地替换；
   全局 npm 安装替换与 profile 切换必须属于同一切点动作。
3. **切点原子化**：快照 → 换包 → 重启 → 健康检查 → 失败自动回滚。
   `dshctl restart-prod` / `install-prod --restart` 已内置该链路，禁止绕过。
4. **保险丝先于负载可靠**：lifeboat 隔离写回按文件串行化 + 唯一 tmp 名 +
   坏 YAML 重建通道（见 `packages/lifeboat/src/patch-file.ts` 头注释）；
   改 lifeboat 自身时先用单测证明写回路径可靠。

## 认证前提

- 官方 browser-auth：启动令牌每进程随机生成、重启即换，只打印到实例 stdout
  （生产在 `journalctl -u dsh-web`）；换取的 cookie 30 天、HttpOnly、
  **绑定具体 host:port**（每个 authority 各登录一次）。
- 取当前认证链接：`dshctl url`（可加 `--host/--scheme` 生成 tailscale 变体；
  `--dev` 面向开发实例）。检索链：access-gate launch-url 端点 → 日志/journal 兜底。
- 脚本一律自签 cookie（`scripts/dshctl/auth.py`，密钥读目标实例
  `.credentials.yaml`，跨重启有效）；`rpc/dev up/pw/session` 已内置。
- access-gate 已合并官方认证：官方 cookie 是唯一凭据，未认证导航渲染
  token 输入页（PWA 内粘贴一次即恢复）；`allowedIps` 为可选附加 IP 围栏；
  `autoLoginTrustedIps=true` 时白名单来源未认证自动铸造官方 cookie（免 token，
  生产已启用——白名单 = tailnet 内全部设备 v4+v6）。

## 适配步骤

1. **锁定目标版本**：npm 版本号或源码 commit 固定（防 master 漂移）。
2. **scratch 验证**：`DSH_HOME=/tmp/<scratch>` 组合配置树、跑通新 CLI；
   对照官方变更清点插件 API 破坏面与去重面（官方已覆盖的能力优先转官方）。
3. **依赖统一升级**：`@deepseek-ai/*` 统一到目标版本，**删除全部旧版兼容代码**（不保留
    fallback 与迁移分支）；
   全仓 `dshctl test` 绿（静态检查 + **类型检查** + 构建 + 单测）。
   类型检查是官方客户端契约破坏的主要捕获点：tsdown 只转译、单测只覆盖已测路径，
   契约字段形状变更（字符串→函数、必填→可选等）只能由 `dshctl typecheck` 拦住。
   完成后仍需按第 7 步在真实 GUI 里过一遍斜杠菜单/设置页等契约密集面。
4. **刷新预设镜像夹具**：用新版本 `@deepseek-ai/dsh-web-app/presets/standard.patch.yml`
   （本机全局安装路径 `@deepseek-ai/dsh/node_modules/@deepseek-ai/dsh-web-app/presets/`）
   覆盖 `packages/agent-preset-lean/tests/fixtures/upstream-standard.patch.yml`
   （保留文件头的来源注释），再跑 `dshctl test`：镜像测试会报出上游新增/改名/改配置的行，
   据此决定把行镜像进 `packages/agent-preset-lean/src/definition.ts`，还是写进 `DROPPED_ROWS`。
5. **本机安装新 dsh**：记录旧版版本号（npm 发布版可直接 `npm i -g <pkg>@<旧版>`
   回滚；未发布版本须保留本机 tarball）；安装动作本身不重启、不影响运行中实例。
6. **切点**：`dshctl install-prod <包> --restart`（或 `restart-prod`）——
   自动快照 `~/.dsh/backups/install-prod-<ts>/`（profile 声明层 + vendor +
   dsh 版本记录）→ 重启 → 健康检查（active + 端口 + index 应答 +
   journal 插件失败扫描）→ 失败自动回滚并二次重启。
7. **验收**：`dshctl url` 取链接在目标 authority 登录；PWA 内经 token 输入页
   登录一次；journal 无 `加载失败/隔离` 新条目。

## 回滚

- **自动**：健康检查失败即还原快照并二次重启；回滚后仍不健康则保留快照并告警。
- **手动**：从 `~/.dsh/backups/install-prod-<ts>/` 还原 `profiles/web/` 声明文件
  （含插件配置所在的 `cordis.patch.yml`）与 `vendor/` →
  `DSH_HOME=~/.dsh dsh plugin --profile web install` → `sudo systemctl restart dsh-web`。
- **全局安装回滚**：npm 发布版直接 `npm i -g <pkg>@<旧版>`（全套平台包，参照
  升级时记录的清单）；未发布版本重装保留的 tarball。重装后必须同步重指 profile
  符号链接池（重启前 profile 与全局安装版本必须一致）。

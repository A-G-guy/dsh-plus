# 仓库管理规范

## 仓库定位

dsh-plus 是 DSH 自定义插件的 pnpm monorepo。设计目标：插件独立分发、可聚合联动、
开发与生产严格隔离。所有频繁操作统一由 `scripts/dshctl.py` 承载，禁止口头/手工流程；
`dshctl` 能力不足允许按规范加强，但仍严禁产生真实费用。

## 包管理

- 包命名统一 scope `@dsh-plus/*`，目录名即包短名（小写 kebab-case）。
- 每包必须独立持有 `version`、`files`、`publishConfig.access=public`——独立分发的底线，
  `dshctl doctor` 会逐包校验。
- 包间依赖一律 `workspace:*`（`pnpm pack` 时自动落成真实版本号）；严禁 `link:` 出现在任何
  包的 package.json 中（`link:` 只允许出现在 profile 的 package.json，由 dshctl 写入）。
- 运行期联动走 cordis 服务（`ctx.provide` / `ctx.inject`），禁止 import 对方包的内部实现。
- **依赖分层红线**（事故沉淀，详见 [adr/0001](adr/0001-平台依赖必须-peer.md)）：
  - 平台包（`@deepseek-ai/*` 全部、`@earendil-works/pi-ai`）一律
    `peerDependencies`（范围如 `^0.2.1-alpha.2`）+ `devDependencies` 精确同版（供构建/类型）。
    平台包由 dsh 宿主提供单实例；声明为 `dependencies` 会被 pnpm 装进生产 profile，
    hoisted 布局下顶层遮蔽宿主实例 → 跨实例 Symbol 错配，工具调度必炸。
  - 第三方包（nodemailer、yaml、https-proxy-agent 等）维持 `dependencies`。
  - `install-prod` 安装前扫描闭包运行时依赖、安装后扫描 profile 顶层实体副本，
    违反即拒绝；`dshctl doctor` 常驻同款检查。
- `@dsh-plus/bundle-main` 是唯一编排层：聚合各【正式】插件的 insert 行与默认 config。
  新增正式插件由 `dshctl new-plugin` 自动登记；单插件脱离 bundle 独立安装必须可用。
- **示例/演示插件（tool-text-transform 等）严禁进 bundle-main**——它们只经 dev profile 的
  用户补丁层注入（`dshctl dev link` 自动维护），避免随 bundle 进入生产、无效占用模型上下文。

## 提交与门槛

- Conventional Commits：`<type>: <简短描述>`，核心变更以 `- <具体变更>` 列出；类型
  feat/fix/docs/style/refactor/test/chore + revert（回滚统一用），可选 perf/build/ci；
  不适用时用 `chore`。由 commit-msg 钩子强制。
- 静态检查：biome（配置 `biome.json`，风格 = 单引号/无分号/2 空格/行宽 100，含 import 整理）。
  `dshctl lint` 只查、`dshctl lint --write` 自动修复并格式化；`dshctl test`/`finish`
  的守门第 0 步即 biome check，error 不过即拒。刻意模式用 `biome-ignore` 行内注释说明，
  不许随手关规则；确需全局例外在 `biome.json` 登记（如 useLiteralKeys 的 `obj['key'] as T`
  断言取值模式）。
- 类型检查：`dshctl typecheck [包...]` 逐包跑 `tsc --noEmit -p packages/<包>/tsconfig.json`，
  第二阶段跑公共契约检查（`tsconfig.contract.json`）；`dshctl test`/`finish` 在 biome 之后
  执行全量检查。tsdown 只转译不做类型校验，官方平台包的客户端契约漂移
  （如 `CommandContribution.description` 由 string 改成函数）不会让构建或单测变红，
  **只有这道闸门能拦住**（漏网案例见 [adr/0002](adr/0002-类型检查纳入守门.md)）。
  用法约定：源码一律带 `.ts`/`.tsx` 扩展名导入（`allowImportingTsExtensions`），
  声明产物由 tsdown 生成（`noEmit`），`@types/node` 必须显式列入 `types`（自动收录对
  `node:` 前缀模块不生效），环境声明 `.d.ts`（如 lucide 深路径通配声明）必须随使用它的源
  文件进 program（`/// <reference path="./x.d.ts" />`——源码级打苞导入时兄弟 `.d.ts`
  不会自动成为 program 根）。修类型错误禁用 `any`/`as any`/`@ts-ignore`/`@ts-expect-error`，
  唯一例外是运行期形状确有保证时的 `as unknown as X` + 就近注释。
- 配置类型禁用 `const X: any = z.object({...})`（会切断 schemastery 推断链，使导出类型
  静默退化为 `any`，tsc 全绿）。正确写法是显式标注 `const Config: z<Input, Output> = z.object({...})`：
  `z.object()` 的推断类型含 cosmokit 的 `& Dict` 索引签名，直接导出会触发 TS2883
  （inferred type cannot be named / not portable）并让 tsdown 的 dts 生成失败，显式标注
  同时解决可移植性与类型保真。Input 侧各字段可省略（schema 有 `.default()`）；注意
  schemastery 输入契约以 `null` 表示「显式置空」、省略表示未设置，故 Input 字段不应并 `| undefined`。
- 公共契约检查（`scripts/contract/contract.ts`）：以**产物视角**消费各包 `lib/index.d.ts`
  并断言关键导出类型。存在意义：逐包 tsc 的 `include` 只含 `src`/`tests`，读不到 `lib/`；
  `skipLibCheck` 又让 `.d.ts` 内部沉默——产物类型退化在逐包检查下全绿。
  新增配置或公共类型时同步补 `Expect<Equal<...>>` 断言；断言必须写在**具体类型**上，
  不可包成带裸类型参数的泛型助手（会触发分布式求值而静默恒真；文件内有自检兜底）。
- 类型闸门覆盖面：`dshctl test`/`finish`/`release publish` 三条主链路 + 根脚本
  `pnpm test` / `pnpm typecheck`。pre-commit 不跑类型检查（退役决策见
  [adr/0009](adr/0009-pre-commit暂存包类型检查退役.md)，闸门本身的决策见
  [adr/0002](adr/0002-类型检查纳入守门.md)）：裸 `git commit` 不会即时跑类型检查，
  提交前必须自行跑 `pnpm test`。本仓无 CI，根脚本与发布链是仅有的强制点。
- 门禁统一为 projects-go（配置 `projects.go.toml`，只记录与内置默认的偏差；下称 pgo）：
  - 检测命令：全量 `projects-go check`、仅暂存 `projects-go check --staged`、
    提交信息 `projects-go commitmsg <文件>`；配置有效性以退出码 0/1 为准（2 = 配置错误，
    会使全部钩子失败，改配置后先验证再提交）。
  - pre-commit（`hook.checks` 默认 doc/index/lines/docsize/secrets/mixedcode/guard）：
    触发时机 = 每次 `git commit`；**按索引判定**（只看本次提交实际带走的内容，未 `git add`
    的草稿不参与），error 阻塞提交、warn 放行。doc 阶段与 `check` 跑同一套文档规则
    （required_fields / scope / append_only / language），并由 `hook.fix` 决定是否顺手
    修复并重新暂存 YAML 时间戳与 INDEX.md（默认为 true，属正常行为）；`check --staged`
    因此与钩子结论一致，提交前用它预演。本仓 AGENTS.md 不设人类手写区，pgo 的
    `agents.enabled` 默认关闭，故无需 `[agents] enabled = false` 之类的关闭项。
  - commit-msg：Conventional Commits 格式与类型校验，不合规拒绝提交。
  - pre-push（pushguard）：拒绝非 fast-forward 推送（改写已推送历史）；确需一次放行用
    `FORCE_PUSH_APPROVED=1 git push --force`。
  - 行数两档（采用 pgo 内置 TypeScript/Python 档位，数值见 `projects-go help lines`）：警告不阻塞；
    拦截只对 baseline（HEAD）之后的新增行生效。存量超限属「既有项」：默认只汇总成一行计数
    （`N pre-existing finding(s) hidden`），`--all` 才逐条列出，`--json` 始终带
    `"deferred": true`；改动其内部即激活为当前项——拆分、精简或在提交说明给出理由。
  - 密钥入库由 secrets 拦截（绝不豁免）；测试/生产同文件由 mixedcode 拦截；
    文档体量由 docsize 拦截（档位见 `projects-go help docsize`）。
  - 失败处理：修问题，不用 `--no-verify` 绕过；回滚用 `git revert`。
  - 钩子为 per-clone：每人首次 `projects-go hook install`（或 `dshctl init-hooks`）；
    pgo 二进制移动后 `projects-go hook install --force` 重装。
- 文档元数据：`last_modified` 与 `INDEX.md` 由 `projects-go doc` / `index` 及预提交钩子
  自动维护，禁止手改；`description` 与 `type` 由 agent 写。`type` 必须为 `fact` 或
  `event`——`projects.go.toml` 把 `docs.required_fields` 提为 error 级。
- **提交判定 = 索引**：`projects-go check --staged` 与 `hook pre-commit` 结论一致（同一批
  层次、同一份索引内容）；`projects-go check` 是不带 `--staged` 的全仓视角，二者都会列出
  被配置关闭的层次（`check skipped disabled layer(s): ...`），不会让关掉的门禁看起来像通过。
- `last_modified` 单一口径：文档内容有未提交改动时写「本次改动/钩子运行时间」，已覆盖该次
  改动的时间戳不再重复刷新（未提交期间不随每次运行漂移），已提交且内容未变时保留原值，
  字段缺失才用该文件上次提交时间补齐；因此时间戳不再滞后一次提交，INDEX 的日期同源。
  历史写错的值不会被追溯纠正，待该文件内容下次改动时归一。
- `type: event` 的文档遵循「只增不改」：判据是索引与 HEAD 的 `git diff -U0`（删除行数 > 0
  即报告），结论需要修正时新开一篇并引用旧篇；`type: fact` 按当前结论覆盖更新。
  该检查为 error 级并由 pre-commit 拦截（见 [adr/0006](adr/0006-提交门禁执行文档规则.md)）；
  `last_modified` 的自动维护改写在判定中被豁免——只动该字段的 hunk 不计为改写，
  因此元数据维护与该检查不再互斥。

## 依赖分层与架构门禁

- 分层模型（内 → 外）：`shared`（工作区共享库，不得依赖任何 `@dsh-plus/*`）→ 功能插件
  （默认互不依赖，联动只经 cordis 服务 `ctx.provide`/`ctx.inject`）→ `bundle-main`
  （聚合编排层，任何包不得 import 它）。例外共三条，均在 `biome.json` 白名单中显式登记，
  理由见 [adr/0008](adr/0008-Actual能力封装以MCP为主源-CLI由部署方提供.md) 与
  [adr/0011](adr/0011-Actual-CLI不进依赖改运行时探测.md)：
  `siyuan-tools → siyuan`、`actual-tools → actual`（子插件依赖主插件的公开契约），
  以及 `actual → actual-mcp`（主插件消费可移植封装层的 MCP 服务端工厂）。
- 强制方式：biome 内置规则，配置在 `biome.json`，随 `pnpm lint`、`dshctl test`/`finish`
  执行，无需额外工具链：
  - `suspicious/noImportCycles`——禁止运行期循环；`import type` 边不计入（本仓 5 个包
    的 type-only 回边属合法模式，跨包与包内文件级一并覆盖）。
  - `style/noRestrictedImports`——包级分层矩阵；禁止 `@dsh-plus/*/src/*` 深路径
    （跨包只经 package.json `exports` 的公开入口，如 `@dsh-plus/shared/client`）；
    禁止 import `@dsh-plus/bundle-main`。
  - `correctness/noUndeclaredDependencies`——src/tests 中 import 的包必须在本包
    package.json 声明；规则经 overrides 限定在 src/tests，因为 `tsdown.config.ts` 直接
    使用根 devDependency `tsdown` 是既有约定。
  - `correctness/noPrivateImports`——禁止导入目标包未导出的私有入口。
- 覆盖面与缺口：以上均为包级/语句级规则，**传递可达性**（如"宿主半不得经任意跳转触达
  浏览器半"）不在其中。该类规则现状 0 违规、属预防性，暂不引入依赖图工具（实测对比与
  决策见 [adr/0005](adr/0005-架构门禁采用biome内置规则.md)）；真出现越界时再补。
- 新增例外：改 `biome.json` 登记被允许的边，并在本文件与 ADR 写明理由；不得用
  `biome-ignore` 逐行绕过架构规则。

## 版本与分发

- 公开发布：`@dsh-plus` scope 已发布到 npm 官方 registry。发版链路统一走
  `dshctl release`：`release status`（本地 vs npm 对照）→ `release bump <包> <规格>`（语义化
  递增，显式版本必须大于当前）→ `release publish [包...]`（测试守门 + 依赖拓扑序发布，
  已发版本幂等跳过）。registry 固定 `https://registry.npmjs.org`（本机默认源是镜像，
  严禁发到镜像）；凭据 = `~/.npmrc` 的 `${NPM_TOKEN}` 插值，环境缺 token 即拒绝。
- **存在性判定只走版本端点**（`common.registry_has_version`，单一事实源）：包文档端点
  带 `Cache-Control: public, max-age=300`，刚发布的版本在 CDN 缓存窗口内读不到，
  据此判定会把"已发布"误判为"待发"——进而重复发布撞 `EPUBLISHCONFLICT`、`finish`
  漏 bump、`doctor --release` 误报。版本端点无缓存头（200/404 即时可信）。
  查询故障一律 fail-loud，**不静默退化成"未发布"**。`release status` 的「待发布」
  是信息性状态（收尾中间态/传播延迟），不计入体检失败、不打警告。
- 开发收尾一条龙走 `dshctl finish [包...] -m "<type>: <描述>"`：测试守门 → 有改动且
  本地版本已上 npm 的包自动 bump（本地版本未发布的包保持原版本直接首发）→
  Conventional Commits 提交 → push → npm 发布 → 本机安装（目标包 ∪ 本次发布包经
  vendor tarball 装进生产 profile）。每步可用 `--skip-tests` / `--no-bump` /
  `--no-commit` / `--no-push` / `--no-publish` / `--no-install` 单独跳过；
  bump 决策需只读查询 registry。重启 dsh-web 不在链路内——必须用户确认后
  另行执行 `dshctl restart-prod`。
- 生产安装唯一路径：`dshctl install-prod <包>`（vendor tarball + overrides 机制，
  详见 ops 文档）；vendor 文件名带内容哈希（`slug-version-<hash8>.tgz`），保证同版本号
  重装也刷新 node_modules，安装后逐文件校验。回滚 = `dshctl uninstall-prod <包>` + 重启。
  生产不直接装 registry 版——vendor 哈希机制仍是最可靠的防陈旧手段。
- 外发只需给 npm 包名：workspace 依赖 publish 时已落成真实版本号，registry 可解析。
- 破坏性变更（插件 id、服务 key、工具名）必须在插件 docs 中记录迁移说明。

## 版本策略（peer 化后解耦）

- 插件版本只随自身变更 bump，不跟随 dsh 平台版本全家桶重发：平台依赖经 peer 范围
  表达兼容区间（如 `^0.2.1-alpha.2`）。**只声明已验证基线这一个范围**：不写并集范围
  （`|| ^…`）、不为旧版宿主留兼容分支，全仓随 `dshctl platform-sync` 一次性换线。
  devDeps 与 peer 的双写纪律（devDeps 必须跟随运行期平台线）见
  [adr/0010](adr/0010-devDeps跟随运行期平台线.md)。
  例外：`@earendil-works/pi-ai` 在 llm-pi 里写成开放上界（`>=1.0.2`）——该插件按文件路径
  动态加载已装 dsh 树里的那份副本，能否工作由运行期形状自检与逐项降级决定，不该由
  manifest 的版本号把它挡在新版 dsh 之外。
- **0.x 的 caret 不跨 minor**：`^0.2.1-alpha.2` 的上界是 `<0.3.0`，宿主一旦跳到 `0.3.x`
  即落在范围外。宿主跳 minor 时若漏跑 platform-sync，dsh 的 `prepareProfileEntries`
  预检会逐行 `disabling profile plugin`——**插件整体「未加载」且没有异常堆栈**，
  只在 stderr 留一句 peerDependencies 不匹配。升 minor 的固定顺序：
  `dshctl platform-sync <新版本>` → `pnpm install` → `dshctl test` → 重装 profile
  （已发布 tarball 的 peer 写在包里，不重装不会变）。
- dsh 平台升级时的动作：跑 `dshctl smoke-prod` 双布局回归 + `dshctl test`；通过则无需
  发版，仅在契约破坏时修复并 bump 对应插件。
- **官方未导出的常量不手抄，改为现场推导**：llm-pi 的 compat 门控表、线协议集合与模型
  条目字段集均从官方安装副本现场推导（协议取 `supportedProtocols()`；门控取 bundle 文本、
  取值约束与字段集取导出的 Config schema，见 `src/official-surface.ts`），官方新增字段/
  协议自动可用；`tests/official-surface.test.ts` 独立复算官方副本守门推导正确性。
  其余镜像点（等价解析链等）仍需人工比对（手抄漏收的案例见 [事故记录](事故记录.md)）。
- 当前唯一受支持基线（已实测）：宿主 dsh `0.2.1-alpha.2` ←→ 插件 peer
  `^0.2.1-alpha.2`（全部平台包；基座 cordis `^4.0.5-alpha.1` /
  schemastery `^3.18.5-alpha.1`）。**不设兼容下限、不为旧版留兼容分支**：
  升级即全仓统一到新基线，旧版适配动作不留档（git 历史即归档）。

## 新增插件流程

```bash
python3 scripts/dshctl.py new-plugin <名字> --type tool|service|persona|ui
pnpm install && pnpm -r build
python3 scripts/dshctl.py dev link && python3 scripts/dshctl.py dev up
```

脚手架自动完成：包骨架、插件级 `docs/`、bundle-main 登记。文档根 glob（`projects.go.toml`
`docs.dirs` 含 `packages/*/docs`）自动覆盖新插件 docs，YAML 与索引由 pgo 维护，无需手改配置。

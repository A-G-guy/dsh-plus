# 事故记录

记录本仓库经历过的事故与静默失败案例（含上游变更引发的），供排查与回归时对照。
分工：**事件叙述（现象/根因/处置/教训）在本篇，决策与后果在 ADR**，两者互相引用、
不重复内容；有 ADR 的事故在 ADR 的状态行登记指向本篇的链接。

新事故追加在文末；已有条目只增不改，结论修正时新开条目并引用旧条目。

## 平台包顶层遮蔽致工具调用全线失败（2026-08-21）

- 现象：生产 dsh agent 一调用任何工具即本轮失败
  `Cannot read properties of undefined (reading 'prepare')`（code UNKNOWN）。
- 根因链：
  1. 生产 profile `pnpm-workspace.yaml` 用 dsh 模板默认 `nodeLinker: hoisted`，传递
     依赖全部提升到 profile 顶层 `node_modules/@deepseek-ai/*`；
  2. 示例插件 `@dsh-plus/tool-text-transform` 把 `@deepseek-ai/dsh-tools` 声明为运行时
     `dependencies`，`install-prod` 装入 profile → pnpm 把一份 **registry 来的第二份
     dsh-tools** 提升到顶层；
  3. dsh 插件加载器以 profile 目录为 baseUrl 解析裸模块：组合树 `tools` 行解析到顶层
     副本，其 `ToolRuntime` 携带该副本的 `TOOL_RUNTIME_SCHEDULER` Symbol；`dsh-agent-loop`
     行解析到安装树副本，持另一份 Symbol；
  4. 两个 Symbol 是不同模块实例的不同对象（文件内容完全一致也一样）→ 工具调用取
     `ctx.tools[全局 Symbol]` 得 `undefined` → `.prepare` 抛错。
- 对照实验：同一实例仅卸载该插件即恢复，唯一变量是"profile 顶层存在平台包副本"。
- 处置：平台包一律 peer + profile 禁止平台副本（安装前后双重扫描）+ 布局留在上游默认
  `hoisted`；决策见 [adr/0001](adr/0001-平台依赖必须-peer.md)。
- 教训：跨模块实例的符号一致性由"唯一一份实例"保证；把平台包声明成运行时依赖，等于
  在生产 profile 里制造第二份实例，且症状离根因极远（工具调度，与包本身无关）。

## 2026-08-30 双死事故（版本错配 + 隔离写回失败）

- 现象：新旧 dsh 版本错配，叠加 lifeboat 隔离写回失败，web 完全不可用；
  只能借外部 agent 工具修复。
- 根因：运行中的 profile 被指向错配版本的插件包；lifeboat 隔离写回在并发下
  不可靠（固定 tmp 名冲突、坏 YAML 强行序列化）。
- 处置：收敛为 [新版适配流程](../ops/新版适配流程.md) 的三条铁律（隔离环境、
  飞行中不换骨、切点原子化）；lifeboat 隔离写回按文件串行化 + 唯一 tmp 名 +
  坏 YAML 重建通道加固。
- 教训：换包与重启必须同属一个切点动作；保险丝（隔离写回）先于负载可靠。

## 斜杠命令菜单全线消失（2026-09-10）

- 现象：生产 GUI 输入 `/` 只剩 Skills 分组，官方全部斜杠命令
  （compact/export/feedback/goal/permission/plan 等）从菜单消失；宿主 RPC
  `commands/list` 却正常返回 7 条。
- 根因链：
  1. 平台升级后官方把客户端契约 `CommandContribution.description` 由 `string` 改成
     惰性求值 `() => string`；
  2. 插件 `@dsh-plus/secret-env` 的 `/var` 命令仍传字符串——它没引用官方契约类型，而是
     **手抄了一份本地结构类型**，抄的是升级前的形状，平台换线时没有任何机制提示副本过期；
  3. `dsh-client-ui-commands` 候选合成期调用 `contribution.description()` →
     `TypeError: contribution.description is not a function`；
  4. `dsh-client-ui-input-trigger` 对源失败的设计是**静默摘除该分组**（只写浏览器 console）
     → 整个 `command` 分组消失，只剩 `skill` 分组。
- 关键点：从构建到单测整条流水线没有一步会因此变红——`dshctl test` 当时 = biome（风格）
  + tsdown（只转译不校验类型）+ `node --test`（运行时），契约形状漂移（字符串→函数、
  必填→可选、字段改名）恰好落在三者共同的盲区，只能在真实浏览器里以运行时异常暴露。
- 处置：逐包 `tsc --noEmit` 纳入守门；消费官方契约改为直接引用官方类型并把对应
  `@deepseek-ai/*` 补进 devDependencies 保同源；决策见
  [adr/0002](adr/0002-类型检查纳入守门.md)。
- 教训：契约类型不得手抄副本（副本自己就是"正确"的，类型检查也救不了）；上游
  "静默摘除分组"的降级设计与本地无类型检查叠加，会把契约漂移放大成整块功能消失。

## settings 承载批量/运行期数据致配置文件膨胀

- 现象：usage-panel 把 models.dev 导入的全量价目（数千条）写进 settings 用户层，
  0.1.7 起 `settings.update` 整值序列化进 profile 的 `cordis.patch.yml`，该文件被写到
  4.3 万行；每次保存都重写全量。
- 同类：lifeboat 的 journal（运行期状态）一度寄居 settings 命名空间。
- 根因：settings 是"纯配置"平面却被用作数据存储，而它是整值序列化、随 profile 声明
  一起落盘的。
- 处置：批量与派生数据一律落插件数据目录（`pluginDataPath`），lifeboat journal 迁至
  `$DSH_HOME/dsh-plus/lifeboat/state.json`；规则见 [插件存储规范](插件存储规范.md)。
- 教训：可公开、可手编、体量小的才进 settings；运行期状态与批量数据一律进插件数据目录。

## settings 整值回写覆盖手工编辑的 patch 文件

- 现象：联调时出现"删掉的 `disabled` 条目复活"、已摘除的配置块被内存值重新写回。
- 根因：运行中的 dsh 实例把 settings 按内存中的活动配置整值序列化写回 profile 的
  `cordis.patch.yml`，实例存活期间的手工编辑会被覆盖。
- 处置：手动编辑纪律——先停实例、再编辑、再启动；改完立即 `/reload` 让内存与磁盘对齐。
- 教训：`cordis.patch.yml` 在实例存活期是"被托管文件"，不要与之竞争写入。

## boot-retry 硬 inject `webServer` 拖垮 headless boot

- 现象：headless profile（无 `webServer` 服务）启动失败，`assertEntriesActivated`
  报 `1 entry did not activate`。
- 根因：初版把 `webServer` 写进模块级 `inject`，服务缺席时该行**永久 pending**，
  即插件让一个本来正常的 profile 起不来。
- 处置：改为 `apply` 内 `ctx.inject(['webServer'], ...)` 惰性等待（服务缺席时本行照常
  active、只是不注册），并补回归用例断言 `inject` 为空数组。
- 教训：可选依赖不得硬 inject；同上，agent-preset-chat 对 `agentPresets` 亦采惰性 inject。

## llm-pi compat 门控表手工镜像漏收官方字段

- 现象：0.1.5-rc.1 官方扩容 compat offer 字段而插件旧表漏收，官方可配字段被本插件
  **误拒**——静默功能缺失、无任何报错。
- 根因：门控表曾是手工镜像，而官方表在 npm 发布形态下不可静态引用（包根不导出、
  `src/` 不随发布），官方扩容无任何机制提示镜像过期。
- 处置：改为从官方安装副本现场推导（`src/official-surface.ts`），推导失败回退内置快照
  且放宽未知键（只拦快照中明确 withhold 的键）；`tests/official-surface.test.ts` 独立复算
  官方副本守门。决策见 [adr/0007](adr/0007-llm-pi目录唯一来源与动态面现场推导.md)。
- 教训：官方未导出的常量不手抄；宁可放宽未知键，不可误拒官方可配字段。

## siyuan-tools 审批策略盲发 ask

- 现象：会话审批策略为 `never`（完全权限）时写调用仍被官方桥接判成
  `the user rejected tool …`，而用户根本看不到弹窗。
- 根因：早期实现不看会话的有效审批策略、一律返回 `{kind:'ask'}`。
- 处置：判定前先读 `ctx.approval` 的有效策略（session 覆盖 → 服务配置默认 → `ask`）；
  `never` 直接放行，审批服务缺席也放行（ask 绝不静默降级为拒绝）。
- 教训：接入官方审批体系时要读策略，不能假定弹窗一定可见。

## 反代缓存头缺失与弱网半截插件包（2026-09-12 弱网增强）

- 现象：移动端弱网下出现半截 JS（插件包传输被截断）；index 被浏览器启发式缓存后，
  用旧启动图请求已失效的插件 URL。
- 根因：反代未对 `/plugins/*` 完整缓冲后按 `Content-Length` 一次发出；`text/html`
  缺少 `no-store`。
- 处置：仓库 `deploy/dsh-proxy.mjs` 三项改造（缓冲 + 截断重试并重压缩；`/assets/`
  哈希产物补 `immutable`；`text/html` 补 `no-store`），实测 5.23 MB → 3.96 MB
  （brotli q5/gzip 重压缩）。现行语义见 [本机部署与重启](../ops/本机部署与重启.md)。
- 教训：静态资源缓存策略要显式声明，不能依赖浏览器启发式规则。

## ui-mobile-fit 死选择器长期静默降级

- 现象：0.1.6-alpha.1 复核时发现 `_detailsCol` 相关覆盖规则自 0.1.5 起即为死选择器
  （上游已改名 `_rightbarCol`），长期只降级回上游原生表现、无任何报错。
- 根因：覆盖式适配依赖上游 CSS Modules 语义后缀，上游更名不会触发任何机制告警。
- 处置：删除死规则、改锚新名；建立"每次升级把全部 `class*=` / `[data-*]` 选择器在官方
  安装树逐一检索"的复核方法。逐版本跟进见
  [ui-mobile-fit 上游跟进记录](../../packages/ui-mobile-fit/docs/上游跟进记录.md)。
- 教训：静默降级机制不报错，必须靠升级时的主动复核兜住。

## Actual 只读工具全线不可用：MCP 结果信封被解包（2026-10-05）

- 现象：`actual` 预设下凡返回数据的调用都读不到内容——数组输出报
  `Tool "…" returned an invalid MCP result: Invalid input: expected object, received array`，
  对象输出则渲染成「returned no model-visible content」；而写操作与业务错误
  （如 `server get-id` 的 `Not found: accounts with name …`）正常可见，
  因此 CLI、认证与服务器三侧都像正常，故障面只在桥接层。
- 根因：主插件的进程内会话把服务端的 canonical `CallToolResult` 解包成业务值后
  才交给子插件，而 DSH 侧 `source: 'mcp'` 的条目由官方 `createMcpToolDefinition`
  注册，其 `call` 会按 `CallToolResult` 校验返回值：裸数组/标量直接判非法，裸对象
  恰好通过校验但 `content` 为空数组。思源实现是原样 `return await client.callTool(…)`，
  此处偏离了参照实现。
- 处置：会话成功时原样交回信封（失败信封仍转异常）；`callToolResultOf` 收敛为
  值→结果的唯一映射，MCP 服务端与 CLI 兜底共用；兜底按 `entry.source` 保持同一
  形状；空输出给 `(no output)` 占位而非空文本。
- 教训：跨层传递官方封装类型时别「顺手解包」——返回值契约由**注册器**决定，
  `source` 一选定形状就必须跟着定；测试只断言「不抛错」会放过整类静默空结果
  （原用例正是只 `await execute()` 而未看结果）。

## Actual 「Budget not found」：syncId 取错字段（2026-10-05）

- 现象：`budgets list` / `server version` 等无预算上下文的命令正常，但
  `accounts list`、`budgets month`、`query run` 等一律报
  `Budget "<id>" not found. Check the sync id of your budget in the Advanced section`。
- 根因：`@actual-app/api` 的两处匹配条件不同——`api/download-budget` 只按
  `f.groupId === syncId` 找远程文件，而下载之后 CLI 的
  `resolveBudgetIdForSyncId` 按 `b.groupId === syncId || b.cloudFileId === syncId` 匹配。
  只读后者的源码就会把 `files.id`（＝`cloudFileId`，服务端 file id）当成 syncId，
  而设置页展示、`downloadBudget` 接受的其实是 `files.group_id`。
- 处置：配置改用 `budgets list` 输出的 `groupId`；卡片 `syncId` 的说明与包文档
  补上「取 groupId，不是 cloudFileId」的辨析。
- 教训：错误文案指向的「settings 页 Sync ID」与代码里的字段名对不上时，
  以**实际参与匹配的那一处**为准；同名 id 并存（file id / group id / cloudFileId）
  的服务端，必须读到真正做判定的那行代码再下结论。

## LLM 应急翻译自动改写屡次失效（2026-10-06）

- 现象：lifeboat「llm-pi 缺席时自动把其配置翻译为官方 llm-pi-ai 并切换默认模型」
  在实际故障中经常无效：改写不生效、LLM 仍不可用，应急承诺落空且无从排查。
- 根因：改写通道建在已废弃的 `settings.yaml` 原始文件上（0.2.x 起 settings 只导入
  含 volatile 字段的段，`llm-pi-ai.providers` 被拒收、滞留 `.imported`）；且翻译
  产物未经官方 schema 与可服务性校验（启发式协议推断 + 字段白名单子集），即便
  写入成功也保证不了官方收下——失效点恰好发生在最没有排错余量的时刻。
- 处置：整套自动改写移除（`fallback-llm.ts`、翻译状态/行级开关/面板 banner/相关
  测试）；改为 llm-pi **常备官方可识别副本** `$DSH_HOME/llm-pi.official-patch.yaml`
  （逐 route 过官方 `Config` 解析 + `resolveProfiles` 校验，写不进官方的绝不落盘），
  lifeboat 只读展示副本状态并告警指引人工应用（`dsh <profile> --patch <路径>`）。
- 教训：应急机制必须先于故障被证明有效——凡「运行期自动改写配置」都必须走官方
  校验缝（schema/解析链），并把最终动作与回退路径显式交还给人。

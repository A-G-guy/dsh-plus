# ADR 0001：平台依赖必须 peer，profile 禁止安装平台副本

- 状态：已采纳（2026-08-21）
- 背景事件：生产 dsh agent 一调用任何工具即本轮失败
  `Cannot read properties of undefined (reading 'prepare')`（code UNKNOWN）

## 事故因果链

1. 生产 profile `~/.dsh/profiles/web/pnpm-workspace.yaml` 配置 `nodeLinker: hoisted`
   （dsh profile 模板默认），传递依赖全部提升到 profile 顶层 `node_modules/@deepseek-ai/*`。
2. 示例插件 `@dsh-plus/tool-text-transform` 把 `@deepseek-ai/dsh-tools` 声明为运行时
   `dependencies`，`install-prod` 将其装入生产 profile → pnpm 把一份 **registry 来的
   第二份 dsh-tools** 提升到顶层。
3. dsh 插件加载器以 profile 目录为 baseUrl 解析裸模块：组合树 `tools` 行解析到 profile
   顶层的第二份副本，其 `ToolRuntime` 携带该副本的 `TOOL_RUNTIME_SCHEDULER` Symbol；
   `dsh-agent-loop` 行解析到 dsh 安装树的全局副本，持另一份 Symbol。
4. 两个 Symbol 是不同模块实例的不同对象（即使文件内容完全一致）→ 任何工具调用
   `ctx.tools[全局Symbol]` 得到 `undefined` → `.prepare` 抛错，本轮运行失败。

对照实验（同一实例仅卸载该插件即恢复）确认唯一变量是"profile 顶层存在平台包副本"。

## 决定

1. **平台包一律 `peerDependencies`**：凡 dsh 宿主安装树提供的包（`@deepseek-ai/*`
   全部，含 cordis/schemastery/cosmokit；以及 `@earendil-works/pi-ai`），插件只允许
   声明为 `peerDependencies`（范围如 `^0.1.0-rc.8`）+ `devDependencies` 精确版
   （供构建/类型/单测）。第三方包（nodemailer、yaml、https-proxy-agent 等）维持
   `dependencies` 不变。
2. **生产 profile 禁止出现平台包副本**：`install-prod` 安装前扫描闭包运行时依赖、
   安装后扫描顶层实体副本，命中即拒绝；`dshctl doctor` 常驻该检查。
3. **生产 profile `nodeLinker` 跟随 dsh 模板默认（hoisted）**：曾短暂切换 isolated
   作"布局双保险"，复盘后撤回——isolated 会把违规副本藏进 `.pnpm/<pkg>/node_modules/`，
   顶层扫描不可见，造成静默坏；hoisted 反而把遮蔽提升到顶层、可被 doctor 检出。
   真正防线是第 1、2 条；布局留在上游默认路径上，避免 dsh 后续更新的未测组合。
   `autoInstallPeers: false` 必须保留，否则 pnpm 自动安装 peer 副本，前两条失效。
4. **回归冒烟**：`dshctl smoke-prod` 用 scratch home + 真实 tgz 安装 + mock LLM +
   内置 bash 工具调用，在 hoisted 与 isolated 两种布局下验证工具调度链路。

## 机制依据（为什么 peer 化后能解析到宿主同一份实例）

dsh 每次 boot 执行 `healProfilesModuleFallback()`：在 `$DSH_HOME/profiles/node_modules/`
铺满指向 dsh 安装树闭包的 symlink。peer 化 + `autoInstallPeers: false` 后，pnpm 不在
profile 内安装任何平台包副本，插件的裸导入沿 Node 解析链向上落到该 fallback 层，
经 symlink 指向**宿主安装树同一份文件**——单实例由平台机制保证，而非靠版本巧合。

`initProfile()` 对已存在的 `pnpm-workspace.yaml` 从不覆写，手工切换 nodeLinker 安全。

## 推论

- 插件版本与 dsh rc 升级解耦：peer 范围表达兼容区间（`^0.1.0-rc.8` 覆盖后续 rc 与
  0.1.0 正式版），dsh rc 升级不再要求全家桶改版本重发；仅在插件自身变更时 bump。
- tsdown 会把 `dependencies` 与 `peerDependencies` 都 externalize（已实测产物确认），
  peer+dev 双写不会改变构建产物形态。
- dev 环境不受影响：dev profile 用 `link:` 依赖，pnpm 不在 profile 安装链接包的依赖，
  顶层永远没有平台副本——这也是本次事故 dev 一直免疫的原因。

# ADR 0001：平台依赖必须 peer，profile 禁止安装平台副本

- 状态：已采纳（2026-08-21）
- 背景事件：生产 dsh agent 一调用任何工具即本轮失败
  `Cannot read properties of undefined (reading 'prepare')`（code UNKNOWN）；
  因果链与对照实验见[事故记录：平台包顶层遮蔽致工具调用全线失败](../事故记录.md)。

## 决定

1. **平台包一律 `peerDependencies`**：凡 dsh 宿主安装树提供的包（`@deepseek-ai/*`
   全部，含 cordis/schemastery/cosmokit；以及 `@earendil-works/pi-ai`），插件只允许
   声明为 `peerDependencies`（范围如 `^0.2.1-alpha.1`）+ `devDependencies` 精确同版
   （供构建/类型/单测）。第三方包（nodemailer、yaml、https-proxy-agent 等）维持
   `dependencies` 不变。
2. **生产 profile 禁止出现平台包副本**：`install-prod` 安装前扫描闭包运行时依赖、
   安装后扫描顶层实体副本，命中即拒绝；`dshctl doctor` 常驻该检查。
3. **生产 profile `nodeLinker` 跟随 dsh 模板默认（hoisted）**：曾短暂切换 isolated
   作"布局双保险"，复盘后撤回——isolated 会把违规副本藏进 `.pnpm/<pkg>/node_modules/`，
   顶层扫描不可见，造成静默坏；hoisted 反而把遮蔽提升到顶层、可被 doctor 检出。
   真正防线是第 1、2 条；布局留在上游默认路径上，避免 dsh 后续更新的未测组合。
   `autoInstallPeers: false` 必须保留，否则 pnpm 自动安装 peer 副本，前两条失效。
4. **回归冒烟**：`dshctl smoke-prod` 用 scratch home + 真实 tgz 安装 + mock LLM +
   内置 bash 工具调用，在 hoisted 与 isolated 两种布局下验证工具调度链路。

## 后果

- 裸导入由平台机制保证落到宿主同一份文件（机制见[官方机制参照](../reference/官方机制参照.md)
  的「profile 模块回退层」），单实例不靠版本巧合。
- tsdown 会把 `dependencies` 与 `peerDependencies` 都 externalize（已实测产物确认），
  peer+dev 双写不改变构建产物形态。
- dev 环境本就不受影响：dev profile 用 `link:` 依赖，pnpm 不在 profile 安装链接包的
  依赖，顶层永远没有平台副本。

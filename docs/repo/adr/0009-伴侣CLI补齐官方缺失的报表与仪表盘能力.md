# ADR 0009：官方缺失的报表与仪表盘能力，用伴侣 CLI 补齐

- 状态：已采纳（2026-10-06）
- 背景：官方 `@actual-app/api` 与 `@actual-app/cli` 都没有自定义报表与仪表盘的
  公开操作面——报表只能在界面里改，仪表盘连 CLI 入口都没有（界面里那个「报告」
  入口点进去就是仪表盘）。Agent 想读报表、算数字或定制仪表盘组件时只能手算或
  引导用户点界面，正是 agent 相对界面更擅长的环节。需要定三件事：
  **能力以什么形态提供**、**内部 handler 怎么够到**、**放进哪个包**。

## 决策一：以伴侣 CLI 的形态提供，不进 profile 依赖

内部 handler（`report/get|create|update|delete`、`dashboard-*`）只在
`api.init()` 返回的实例上可用（`lib.send(name, args)`），公开 API 不暴露。
要在进程内直连，就得把 `@actual-app/api` 装进 profile：实测其闭包约 236MB
（better-sqlite3 + sql.js + absurd-sql + hyperformula + date-fns 等），
而 profile `web` 的 node_modules 当前只有 74MB，代价不成比例。

因此做成**伴侣 CLI**（`@dsh-plus/actual-reports`，bin：`actual-reports` /
`dsh-plus-actual-reports`）：零依赖、零版本声明，运行期从**已检测到的官方 CLI**
解析 api 路径（`createRequire(<cli entry>).resolve('@actual-app/api')`），
并与官方 CLI 共用同一份预算目录、同一套锁协议与缓存判定。CLI 版本仍由部署方
决定，本包不校验、不钉死、不打包它；解析失败即显式报错并说明补救方式。

## 决策二：作为声明式扩展并入能力目录，而不是伪造 help 树

`@dsh-plus/actual-mcp` 的能力主源仍是官方 CLI 的 help 文本；报表/仪表盘两族
的**动作表在源码里**（`src/actions.ts` 一处驱动 argv、帮助与工具 schema），
经 `entry.reports` 执行计划入目录。由此：

- 主插件的 `mapTools` 从 MCP `tools/list` 派生目录时，把这两个扩展条目并入
  （官方服务端不提供它们，不会出现在 `tools/list` 里）；
- 交叉校验把扩展族名单独传入 `computeDrift`，它们既不算 MCP-only 也不算 CLI-only，
  不会把有意扩展报成漂移；
- 派生的 JSON 工具在独立 stdio 入口（格式一）里同样可用——MCP 宿主无需知道
  这个族来自伴侣 CLI。伴侣 CLI 不可解析时条目**不入目录**，只记一条告警：
  宁缺不假，绝不挂一个调不动的工具。
- 官方 CLI 与伴侣 CLI 共用 `ActualCli` 的**同一条串行队列**（`runWith`）：
  两条链路都要读写同一份预算目录，并发只会自伤。

## 决策三：放在新包 `@dsh-plus/actual-reports`，登记第四条分层例外

报表与仪表盘属同一领域（报表经 `custom-report` 组件上仪表盘）、共用同一套会话/
锁/缓存/配置与错误模型，故同包两族；不进任何预设的操作面清单以外的地方，
`bundle-main` 不做改动（它不是插件行，靠 `actual-mcp` 的依赖带上）。

新增分层例外：`actual-mcp → actual-reports`（封装层消费伴侣能力描述符）。
它是本仓第四条例外，与 `actual → actual-mcp` 同源同理：方向仍是外层依赖内层，
只是能力来源不止官方 CLI 一个。理由与清单同步登记在
[仓库管理规范](../仓库管理规范.md) 与 `biome.json`。

## 后果

- 报表数字不再需要 agent 手算：`report data` 按官方口径本地复算并给出逐区间明细；
- 仪表盘组件（含把报表放上仪表盘的唯一路径 `custom-report` + `meta.id`）可增删改；
- 官方 API/CLI 升级带来的字段漂移风险集中在两族动作表与 `dashboard-store` 的
  校验点上，均有显式错误兜底；未支持的旋钮（`groupBy=Tag`、`balanceType=Budgeted`）
  报错而不是算错；
- 代价是新增一条需要维护的依赖边，以及「api 路径解析」这一处运行期脆弱点——
  它被显式错误与 `--api-path` 兜底覆盖。

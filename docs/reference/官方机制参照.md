# 官方机制参照

本文件记录经本机 npm 安装核实过的 DSH 插件机制结论；权威来源是安装树内各包的 README：
`/home/agguy/.npm-global/lib/node_modules/@deepseek-ai/<pkg>/README.md`
（每包附 README.zh.md）。版本基准：`@deepseek-ai/dsh@0.2.0-rc.1`（npm 发布版）。
安装树布局：干净安装（scratch/仓库）下平台包平铺于同一 `node_modules/@deepseek-ai/`；
本机**全局树**因历史版本残留，新平台包嵌套在
`@deepseek-ai/dsh/node_modules/@deepseek-ai/` 下，顶层同名旧版副本不参与运行
（0.1.6 与 0.1.5 的安装布局规则相同，嵌套只源于旧版残留，非版本差异）。

> 0.2.0-rc.1 相对 0.1.7 的破坏性变更（本仓适配点，2026-09-29 实测）：
> - **兼容预检按 peer 判定，范围不覆盖即整体禁用**：boot 期 `prepareProfileEntries`
>   读每个 profile 行 manifest 的 `peerDependencies[@deepseek-ai/dsh*]`，与运行时版本
>   不符即 `dsh: disabling profile plugin …` 并置 `disabled`（bundle 行则整包
>   `skippedBundles`）。`^0.1.7-rc.1` 不覆盖 `0.2.0-rc.1`（0.x caret 上界 `<0.2.0`）
>   → 升级后插件全部「未加载」、无异常堆栈。仓内统一改 `^0.2.0-rc.1`
>   （`dshctl platform-sync 0.2.0-rc.1`），**兼容下限即 0.2.0，不回兼容 0.1.x**。
> - `DeepSeekAdapterOptions.resolveApiKey` 删除，改为
>   `resolveAuth: (connection) => Promise<DeepSeekRequestAuth>`：认证头由插件一次性给出
>   （`{ headers, onRequestError? }`）。官方 `llm-deepseek-api-key` 接线为
>   `{ headers: { 'x-api-key': key } }`，与 0.1.7 适配器内部设置的头一致。
> - `DeepSeekAdapter.listModels` 改读 `dependencies.discoverModels`（缺省返回 `[]`）：
>   不传即模型目录为空；官方接线用 `catalogModelInfo(provider, model)` 映射
>   `connection.models`。`providerName` 选项可取代 `providerInfo` 覆盖。
> - 文件索引作用域改用 `connection.headers` 参与哈希（0.1.7 用 `apiKey`），由适配器
>   内部 `RequestFiles` 组装，插件侧无感。
> - `@deepseek-ai/dsh-llm-deepseek` 包根不再导出 `apply/inject/name`（新增
>   `registerDeepSeekProvider` / `deepSeekConfigFields`）；`dsh-llm` 新增
>   `ACCOUNT_QUOTA_EXCEEDED_CODE` / `projectToolUpdates`；`dsh-session` 新增
>   `ToolCallRecovery` / `ToolHistoryProjection`；`dsh-client-ui-primitives` 删除
>   `CODE_HIGHLIGHT_EXTENSIONS` / `languageForPath` / `OnboardingSurface`（本仓均未使用）。
>
> 0.1.7-alpha.2 相对 0.1.6 的破坏性变更（本仓适配点）：
> - `dsh-settings` 删除 `installSection` 与 `get`：读用
>   `settings.describe().find(r => r.ns === ns)?.value`（平面值）；插件 `Config`
>   顶层字段需逐个 `.volatile()` 才会进 describe 视图（否则配置卡片无数据）。
> - 事件 `settings/updated` 改名 `settings/document-updated`，载荷 `(ns, revision)`。
> - `settingsScope` 服务删除，官方卡片改走 `configForms`
>   （`@deepseek-ai/dsh-client-ui-settings`）。
> - `SettingsProvider` 类型不再从 `@deepseek-ai/dsh-settings` 导出（默认导出即
>   `SettingsForms` 类；`register` 已删，读写为 `describe/update/replace/mutate`）。

## 启动与 profile

- `dsh --profile <name>` 启动 `$DSH_HOME/profiles/<name>/`；`dsh web` = `--profile web` 别名。
- `web`/`headless` profile 首次使用自动从模板初始化；其余 profile 由 `dsh plugin` 创建。
- profile 组合树层叠顺序：bundle 列表（`package.json` 的 `dsh.profile.bundles`，按序）
  → profile 的 `cordis.patch.yml` → home 级 `$DSH_HOME/cordis.patch.yml` → `--patch` 覆盖层。
- `dsh --profile <name> --dump-config` 不启动即可预览组合树（改编排后必查）。
- bundle 解析顺序：dsh 安装目录优先（官方 bundle），然后 profile 自己的 node_modules。

## 插件安装

- `dsh plugin --profile <name> <args>` = 在 profile 目录转发 pnpm。
  因此 `add <pkg>`（registry/tarball）与 `add link:<路径>`（本地开发）都合法。
- 已验证的最小实例：`/tmp/dsh-test-mono`（插件 + 共享库）与 `~/.dsh/profiles/testdemo`。

## patch 层语义（cordis.patch.yml）

- 顶层数组；行级操作：`- insert: [{id, name, config?}]` 新增插件行；
  `- id: <已有id>` + `config:` 整行替换目标 config（须重述全部字段）；
  `- id: <id>` + `disabled: true` 禁用。`!!js` 表达式可用。
- **用户 patch 层热应用**（0.1.2-alpha.2 复核不变）：profile `cordis.patch.yml` 与 home 级
  `$DSH_HOME/cordis.patch.yml` 的改动由 dsh-app-boot `watchUserPatches` 监听
  （HMR registerConfig → root Include entry.update），事务性重放——运行期改
  patch 文件**无需重启**；顶层非数组/不可解析在 boot 期 fail-loud。
- loader 条目 `disabled` 热转：update 时禁用即 dispose fiber，启用即 init；
  组行（`group: true`）disabled 级联全部子行（`_disabled()` 沿 owning parent 链）。

## agent 预设平面（0.2.0-rc.1 复核）

- 预设 = 组合声明行：`@deepseek-ai/dsh-agent-preset` 包装行经
  `agentPresets.register(声明)` 注册（`id` + `name/description/order` +
  子插件行列表）；registry **不扫目录、不接受预设路径、不写声明**——
  `~/.dsh/.agent-presets/` 自此无读取方（官方技能
  editing-cordis-compositions 同此）。
- 新增/覆写预设的官方路径 = bundle/profile patch `insert` 一个
  `@deepseek-ai/dsh-agent-preset` 行（或经插件注册，如 dsh-plus 的
  `packages/agent-preset-chat`）；`readDocument(id)` 把声明渲染回
  entry-list YAML 供查看，无回写入口。
- 每条声明在 registry 专属 scope 内急切建树；声明更新/移除即退役旧
  revision，已绑定 Agent 与临时读持有引用照常工作——新会话走当前声明，
  已加入会话保持原组合，无需重启进程。
- 激活审计（import 失败 / 服务缺失 / 服务泄漏）拒绝挂载并保留 `list()`
  broken 诊断；等待 Host 服务的行在 Host 树落定后自愈复审，**启动次序不
  决定结果**（因此注册方不应在自身激活内同步等待注册完成，参考
  agent-preset-chat 的后台注册写法）。
- 默认预设 = `agent-preset-registry` 行 config 的 `default`（部署默认）与
  `selectedDefault`（volatile 用户选择，新会话在其上覆盖解析）；
  `list()` 含 broken 原因，`remove` 语义由声明退役（patch 移除行）承担。
- host 平面被 web-app bundle 禁用的行（tool-subagent 等）在 preset 内由
  standard/code 预设提供；禁用 preset 组行（如 `delegation`）即整体关闭该能力。
- 0.1.2-alpha.1 起官方提供子代理模型路由授权（`subagent-model-selection` settings 段
  + `list_subagent_models` 发现工具 + 执行器强制校验），fork 刻意不允许改路由
  （KV Cache 前缀复用）；spawn 的部署级默认走 tool-subagent 行 `Config.agentOptions`。
- 官方授权是"主代理可选的模型白名单"，不强制默认路由：主代理未显式传
  provider/model 时子代理继承主代理路由。管理端强制默认由
  `@dsh-plus/subagent-model` 补齐（按 provider 注入 agentOptions，见其 docs）。

## 服务端插件契约

- 导出 `name`（必填）、`inject`（可选）、`Config`（schemastery，可选）、`apply(ctx, config?)`。
- bundle 包额外声明 `dsh.bundle.patch: ./cordis.patch.yml`，其 insert 行随 bundle 层生效。
- 工具注册：`ctx.tools.register(defineTool(...))`（权威：`dsh-tools/README.md`）；
  执行管线：`tools/pre-execute` → guards → `tools/execute` → `tools/post-execute` →
  `finalizeContent` → `tools/result`。
- 服务联动：`ctx.provide(key)` / `ctx.plugin(Class)` / `ctx.inject([...])`（cordis 标准）。
- **服务可见性（0.2.1-alpha.1 实测）**：宿主在 boot 的 prepare 阶段挂到根上下文的服务
  （`profileContext`、`pluginPackages` 等）能被任意行的 `ctx.get(name)` 读到；而**行内服务**
  （`webServer`/`commands`/`agents`/`hmr`…由某行插件提供）在其它行的 `ctx.get` 里恒为
  `undefined`，必须走 `ctx.inject([...], cb)`（= 挂一个 inject 声明的子插件，依赖就绪才跑）
  或静态 `inject` 声明；未声明就做属性访问（`ctx.hmr`）会直接抛
  `cannot get property "x" without inject` 并让该行 FAILED。
- **可选依赖的写法**：boot 期（`apply` 执行时）同级服务尚未就绪，`ctx.get` 一律读不到；
  因此「有就用、没有就降级」的能力位应当在**用的时候**经 `ctx.inject` 回调捕获，并接受回调
  延迟触发——`hmr` 的 fiber 要等模块监听 ready，本机以整仓 packages 为监听根时实测晚于
  boot 6 秒以上，早于此调用会读到「无 hmr」。

## UI 插件契约

- 包 `exports["./client"]` 指向浏览器半构建产物（CJS factory bundle）；
  `dsh-client-modules` 把启用行的 client 包扫描进 `window.__DSH_BOOT__` 并经 `/plugins` 提供。
- `dsh-client-hmr`：stat 轮询构建产物，任何 tsdown watch 重建都会触发浏览器单插件热更；
  重载是粗粒度的（React 状态丢失），失败不回滚（entry 标记 FAILED）。
- 插槽/挂载体系见 `dsh-client-ui-slots`、`dsh-client-ui-*` 各包 README。
- 0.1.5 及更早：「设置 → 插件 → 可配置」页（ConfigurablePluginsTab）按命名空间配对
  分发 `settings.plugin.item` 插槽的第三方卡片（keyed by settings 命名空间）；
  0.1.6-alpha.2 起该页迁入侧边栏独立「插件」页（dsh-client-ui-plugin-manager），
  旧槽位删除，第三方卡片改挂 `plugins.row.config`（key = `<bundle 包名>#<row id>`，
  行详情页分发 `view: 'summary' | 'page'`）或 `plugins.bundle.config`（key = 包名）。
  本仓库经 shared 层 `injectPluginConfigCard` 三槽位同注册兼容两个时代；配置读写经
  `ctx.remote.settings`（0.1.2-alpha 线起 host-apiproxy 及其白名单已删除，第三方命名空间
  全量开放）。
  `settingsScope` 服务已随 0.1.7 删除（官方卡片改走 `configForms`）；0.1.6 及以前
  其 bind 在非 loopback 页面固定 memory 模式——插件卡片自始走
  `ctx.remote.settings` 直连（本仓库 shared 层 `createSettingsScope`），
  并配合 remote-settings 插件修复官方 mirror。

## LLM 路由机制（dsh-llm / dsh-llm-pi-ai）

- `PiAiAdapter` 构造 seam：0.1.2-alpha 线起 `auth`（credentials + authContext）为必需，
  `resolveApiKey`/`resolveAttachments?`/`resolveImageAccess?` 为回调钩子；schema 校验在
  adapter 之外的 catalog 层（COMPAT_GATES 按协议门控，**写时拒绝**不适配字段）。
- `ctx.llm.registerAdapter(routes, adapter)` 是结构识别（无 instanceof）；
  重名 route 抛 `DUPLICATE_ADAPTER`；handle 有原子 `replace(routes)`。
- 官方配置层已支持目录继承（route 同名内置 provider / models 列表 / modelOverrides）与
  发现（discovery）与 OAuth 登录；compat 不再静默丢弃而是写时拒绝。
- 模型目录不再产出 `imageDetail`（写时抛错），改用 `imagePixelBudget`/`imageMaxBytes`。
- `registerConfigurableProviders([])` 抛 `INVALID_DIRECTORY`（空目录不可注册）。
- 启动期条目 apply 失败会导致整个 profile 启动失败（loader 不隔离启动期条目异常）。
- schemastery 陷阱：array 字段缺省物化为 `[]`（需要"未设置"语义时给显式 `.default()`
  或在消费端把 `[]` 当未设置）；settings 层 `deepFreeze` 过的解析值不能再通过带键约束
  dict 的 schema 二次校验（冻结对象校验失败）——不要对 `scope.get()` 结果再跑 schema。
- 0.1.7 起 `installSection`/setSource 删除：volatile 字段为活动引用，消费端
  `current = () => unwrapVolatile(config)` 每次现取；变更事件
  `ctx.events.on('loader/volatile-update', ...)`；写入校验走 `internal/config`
  waterfall（handler throw 即拒）。

## 注意事项

- patch 的 config 覆盖是整行替换：改一个字段也要重述整行 config。
- 工具参数校验由 registry 在 execute 前完成，非法参数不会进入工具体。
- `run_code` 是保留工具名（Code Mode 传输），不可注册同名工具。

## 桌面端与 profileContext

- 官方桌面端（DSH Desktop，Electron）拥有独立 `desktop` profile：配置在
  `$DSH_HOME/profiles/desktop`，插件经 GUI「设置 → 插件」安装（桌面端内置
  pnpm 管理）；`dsh/lib/bin.js` 拒绝 `--profile desktop`（CLI 不管理该 profile）。
  默认端口 19387（web 为 3080）；GUI 经 `dsh-app://app/` 加载并做 HTTP/IPC 转发。
- `ctx.profileContext`（官方运行时事实，`dsh/lib/profile-boot-*.js` 注入，
  `dsh-app-boot` 提供类型声明）：`{name, dir, patchPath, installAnchor, cwd, home,
  startedBundles, overlays, telemetryDisabledEnv}`，经 `ctx.get('profileContext')`
  取用（optional，无需 inject）。本仓库用法：
  - lifeboat `patchFile` 缺省取 `profileContext.patchPath`（无 profileContext 的
    组合树告警停用故障隔离，不再猜默认路径）；
  - reload 以 `profileContext.name === 'desktop'` 作为桌面端门控；
  - llm-pi 的 dsh 树锚点链优先 `profileContext.installAnchor`，其次
    `realpath(argv[1])`（桌面端 Electron 启动时 argv[1] 是 Electron 自身，
    锚点是唯一可靠来源）。

## 客户端平台与热更

- `dsh.client.platform` 仅接受 `"web"`（官方条目全部为 web）：桌面端复用同一
  `dsh-client-modules` 客户端装载路径，没有独立的 desktop 平台值。
- 客户端 bundle 是 CJS factory（react 等经模块表 require）；client 代码不得
  import `node:*`（浏览器拿不到）——跨平台路径判据用字符串逻辑或官方
  `@deepseek-ai/dsh-util-workspace-path`（`isAbsoluteWorkspacePath`/`pathPartsOf`）。
- `dsh-hmr` 配置热重载在 web+desktop 默认开启；官方无插件级 restart API，
  「重启进程」类能力（本仓库 reload 插件）只能走 systemd（Linux），
  桌面端/Windows 显式降级（按钮置灰 + 提示）；Electron 是否暴露重启 API 未实测。
  相关补充：启动器提供了 `ctx.appExit`（经 `dsh-cmdline` 的 `provideCmdline`
  注入，`profile-boot` 侧接线到有界优雅退出）——它是「退出进程」而非「重启」，
  退出后是否回来取决于外部监管（systemd `Restart=always` / Electron / 人工）。

## 热重载与 reload 能力边界（0.2.1-alpha.1，2026-10-03 实测）

- **配置层**：`hmr` 行在提供 `profileContext` 时默认启用、`root: []` —— 只热应用
  profile 补丁、home 补丁、profile manifest 三类文件，走
  `readProfilePatches` + `reconcileProfilePatches`（两者皆为公开导出，
  `dsh-config-editor`/`dsh-plugin-manager` 同款用法）。要监听**模块代码**，按官方
  README 在 profile patch 配 `- id: hmr` + `config.root`。
- **模块替换的硬边界**：只有模块路径**不含** `/node_modules/` 才替换。`loadDependencies`
  对该片段直接返回空集（`dsh-hmr/lib/index.js:447`），随后 `dependencies.length === 0`
  使该条目被跳过（同文件 :882）——已安装包（生产 profile 的 tarball 布局）永不被替换。
- **实测三方对照**（dev 实例、mock LLM、探针写命中文件，同一 PID 内观察重新 load/apply）：
  profile 内普通路径模块编辑后 ~0.5s 内被替换；symlink → 真实路径（等价 `link:`
  安装）同样被替换；`node_modules` 内真实副本（并显式放开 `ignored`）**无任何反应**，
  属静默忽略。
- **客户端**：`dsh-client-hmr` 每 500ms stat 轮询每个客户端 bundle，`clientModules.rebuilt`
  重算 rev 并经 `/plugins/events` 推 `graph`/`rebuilt` 帧 → 浏览器侧插件替换
  **不需要刷新页面**；host 重启后若产物未变 rev 不变，重连不会做无谓替换。
- **指令文件**：`dsh-agent-instructions` 无监听/无刷新 API —— 首个请求注入基线，
  之后只在文件操作触摸、新会话、恢复会话时对账；`AGENTS.md` 的会话内编辑**无法**
  被进程内重载覆盖。
- **系统提示**：每次请求现场渲染（`system-prompt` 的 `renderPrompt(assembly)`），
  行变更即时反映；技能侧 `dsh-skill-filesystem` 自带 watch + `skills/change`。
- **官方对「换包」的立场**：`dsh-hmr` 已知限制写明「通过插件管理器替换已安装包版本
  仍需要重启」；`dsh-plugin-manager` 写明「覆盖已安装的包不发布，并报告
  `restart-required`」。`file:`/`link:` 是官方支持的 profile 依赖 spec
  （`parseInstallSpec` 归为 `kind: 'path'`，`listBundles().source` 解析为绝对路径），
  但官方不把它当作热替换手段。
- **HMR 全量重载路径不生效**：externals 变更时 HMR 调 `loader.exit()`
  （`dsh-hmr/lib/index.js:760`），而随包发布的 loader 该方法是空实现
  （`cordis-plugin-loader/lib/index.js:665`），故不会触发进程退出。
- **本仓用法**：dev profile 由 `dshctl dev` 注入 `hmr.root`（workspace packages），
  使 `pnpm -r build` 后的插件在运行实例内即时替换；生产 profile 的 tarball 布局
  只能重启，`@dsh-plus/reload` 用产物指纹把这类变更点名报告。

## Windows 运行时要点

- 官方上游 Windows 为 bash↔pwsh 双轨（`process.platform === 'win32'` 判定），
  进程树终止用 `taskkill /PID <pid> /T /F`；无 systemctl/journalctl。
- Node 侧易错点：`os.kill(pid, 0)` 在 Windows 会【直接杀进程】，存活探测须用
  `tasklist`；`.cmd/.bat` 须经 `cmd /c` 启动；PATH 分隔符按被发现平台取。
- 路径：盘符（`C:\`）、UNC（`\\server\share`）、`\` 与 `/` 混用都要覆盖；
  客户端无 node:path，判据须字符串实现（本仓库 web-files 见 `src/paths.ts`）。
- 解释器：Windows 不保证存在 `python3`，须 PATH 扫描 + `py -3` 兜底
  （web-search-services `src/python.ts` 候选链）。
- 仓库工具链（`scripts/dshctl.py`、测试脚本）仅 Linux，不做 Windows 化
  （范围经用户确认）。

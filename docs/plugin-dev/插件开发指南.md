# 插件开发指南

## 通用契约

插件 = ESM npm 包，cordis 约定导出：

```ts
export const name = 'dsh-plus-xxx'        // 加载器标识
export const inject = ['tools'] as const    // 依赖的服务（可选）
export function apply(ctx: Context): void   // 入口
```

构建：tsdown（`pnpm -r build`），产物 `lib/`，`exports` 同时暴露 `./src/*` 便于源码级调试。

## 四类插件

### tool（工具）

`ctx.inject(['tools'])` 后 `ctx.tools.register(defineTool({...}))`：

- `parameters`/`output.schema` 用 dsh-tools 的 schema DSL（注意：顶层 object 不写 `required`，
  属性级写 `required: true`）；`defineTool` 会在 execute 前做参数校验，非法参数在边界即被拒。
- `output.render(args, value)` 返回模型可见内容块；`timeoutMs` 必须为正有限数。
- 纯逻辑抽到 `@dsh-plus/shared` 或包内独立模块，单测只测纯逻辑（见 tool-text-transform）。
- 参考实现：`packages/tool-text-transform`（官方参照：dsh-tool-todo）。它是 dev-only 示例：
  不经 bundle-main 进生产，只由 dev profile 的 cordis.patch.yml 注入，供 smoke 与调试。

### service（大功能）

`ctx.provide('<key>')` + `ctx.plugin(Class)` 暴露服务；消费方 `ctx.inject(['<key>'])`。
这是插件间联动的正统通道。模板：`dshctl new-plugin <名> --type service`。

### 外部脚本桥接（特例，默认 TS 原生）

集成外部 HTTP 服务**默认 TS 原生**（进程内 fetch、编译期契约）。仅当复用一套
已维护、逻辑非平凡的外部编排（skill/CLI 脚本）时才允许整体桥接其脚本，且必须：
随包维护脚本单向副本（`scripts/` + README 声明由来/同步策略）、在包 docs 标注
特例身份、失败域/超时/密钥注入在薄适配层兜住。判定标准与决策记录见
[ADR 0003](../repo/adr/0003-搜索provider默认TS原生-Python桥接为例外.md)，
参考实现：`packages/web-search-services`。

### persona（提示词）

两条路线：① bundle/profile 的 `cordis.patch.yml` 覆盖 `id: system-prompt` 行的 `persona`
文本（简单、声明式，官方 dsh-web-app 即如此）；② 注入 `systemPrompt` 服务注册 section
（动态、可组合）。模板注释内有指引，权威契约见官方机制参照文档。

### ui（界面）

包提供 `./client` 导出（浏览器半），tsdown 构建为 CJS factory bundle；
`dsh-client-modules` 扫描启用行的 `dsh.client` 包进 `window.__DSH_BOOT__`，
`dsh-client-hmr` 轮询构建产物实现热更（跑 `tsdown --watch` 即可热重载，无需重启进程）。
挂载点走 `dsh-client-ui-slots` 插槽体系。

实测要点（参考实现：`packages/ui-mobile-fit`）：

- 浏览器半产物必须是 `window.__ModuleLoader__.load({id, factory})` 形式
  （`factory(require)` 体内是 CJS，自由变量仅 `exports`/`module`/`require`）。
  tsdown 没有现成 preset，用 `format: 'cjs'` + `outputOptions.banner/footer`
  包出外壳即可；`entryFileNames` 固定为 `client.js`。
- `package.json` 必须带 `"dsh": {"client": {"inject": [...], "platform": "web"}}`
  标记，`dsh-client-modules` 才会扫描 `./client` 导出。
- 样式注入沿用官方约定 `<style data-plugin="<pkg>" data-plugin-css="<pkg>/<file>">`，
  HMR 按此卸载；清理逻辑放进 `ctx.effect` 的返回函数。
- 脚手架（`new-plugin --type ui`）只生成 node 半骨架，上述客户端半需手工补全。
- 覆盖式适配上游界面时：上游类名是 CSS Modules 哈希（前缀随构建变、语义后缀稳定），
  用 `[class*="_语义后缀"]` 子串选择器；对抗内联样式才用 `!important` 并注释。
- 浏览器半使用 cordis 服务（如 `ctx.slots`/`ctx.locale`）时，客户端模块必须导出
  `inject`（服务 key 列表，如 `['slots', 'locale']`），否则报
  `cannot get property "<key>" without inject`；package.json 的 `dsh.client.inject`
  列的是**包名**（加载顺序），两者职责不同，都要写。react/react-dom 由外壳
  ModuleLoader 提供，tsdown 标 external 即可（factory 内 `require('react')`）。
- 运行时 import 的**第三方**包必须进 `dependencies`（tsdown 只 externalize
  dependencies 与 peerDependencies，devDependency 会被打苞进产物）。
  **平台包例外且必须 peer**：`@deepseek-ai/*`（含 cordis 的 `Service`/`Context`
  值导入）与 `@earendil-works/pi-ai` 一律 `peerDependencies` + `devDependencies`
  双写——宿主提供单实例，打苞或装副本都会造成跨实例符号/类身份错乱
  （详见 docs/repo/adr/0001）。纯类型导入（`import type`）只需 devDeps。

### 带配置界面的插件（settings 命名空间 + 配置卡片）

参考实现：`packages/notify-email`。要点：

- 配置单一事实源是一份 schemastery schema，同时充当 cordis 行级 `Config`（组合默认）
  与 settings 用户层（loader 把用户层 override 并入行级 config：顶层字段全部
  `.volatile()`，GUI 写入经 profile patch 落盘、loader 原位提交活动引用；消费端
  `current = () => unwrapVolatile(config)` 现取即热），`settings.update` 写入即 profile
  行级覆盖层 `cordis.patch.yml`（`$DSH_HOME/settings.yaml` 已废弃，仅启动时
  一次性并入），热生效；**批量/派生数据（导入结果、目录快照等）不得走 settings**——
  整值序列化会淹没配置文件（案例见 [事故记录](../repo/事故记录.md)），
  一律落 `pluginDataPath` 插件数据目录；secret 字段标 `.role('secret')`。
  **schema 必须显式标注**：`export const Config: z<ConfigInput, ConfigFields> = z.object({...})`
  （字段逐个 `.volatile()`；`ConfigFields = VolatileFields<ConfigPlain>`，消费平面类型
  `Config = UnwrapVolatile<ConfigFields>`，`VolatileFields`/`UnwrapVolatile` 均
  `import type` 自 `@dsh-plus/shared`）。不要写
  `const Config: any = z.object({...})`——它会切断推断链，使导出类型静默变 `any`
  （未知键与错类型赋值全部通过，而 tsc 全绿）。嵌套 schema 同样逐个标注，
  推荐复用已导出的 `*Entry` 类型作为 Output，避免「schema 一份、类型一份」两处漂移。
- **文案键类型**：i18n 字典用 `as const` 声明，导出
  `type DictKey = keyof typeof commonZh | keyof typeof ownZh` 与 `Translate`，
  `en` 标注 `Record<DictKey, string>`。这样 `t('...')` 的键名拼写与中英键对齐都在
  编译期受检。运行期才确定的键（如端点返回的错误码）走显式收窄（`Object.hasOwn` 守卫），
  不要为绕过检查而把 `Translate` 放宽回 `(key: string) => string`。
- **跨半类型**：宿主窄面（slots/locale/remote）从 `@dsh-plus/shared/client` 导入
  （`PluginClientContext<DictKey>`），不要在插件内重复声明。类型只跨半共享时用
  `import type`（编译期擦除，不进 client bundle）。结构化 wire 数据建议集中在
  `src/dto.ts` 单一门面，客户端 `import type` 消费。
- **客户端边界**：`getJson`/`postJson` 接受可选类型谓词 `guard`；对结构性 payload
  （数组字段被直接 map 的）传入守卫，畸形响应会在边界 fail-fast，而不是渲染期白屏。
- **配置数据通道**：第三方命名空间对 `settings.*` RPC 全量开放（无白名单）；
  浏览器半配置卡片统一经共享层 `injectPluginConfigCard` 注册（插件页两个 keyed
  槽位：`plugins.row.config` / `plugins.bundle.config`；旧的 `settings.plugin.item`
  槽位不存在，本仓不再注册），读写经共享层直连 `ctx.remote.settings`
  （官方 `settingsScope` 服务不存在、由 `configForms` 取代；直连使远程页面同样可用）。
- **卡片只输出无边框分节**：宿主插件页自己画标题、图标、面包屑与描述，并把配置
  视图放进已有页面内边距的容器（`div.detailSections[data-plugin-config]` 或
  `section.detailSection[data-plugin-config]`），外层无边框。因此 `CardChrome` 一律
  输出**无边框分节**（小节标题 13px/600、字段区、非 sticky 页脚、横向零内边距）；
  再套一层自绘卡片就是卡片套卡片，会把移动端可用宽度逐层扣掉（页面已占掉
  `clamp(24px,4vw,48px)`×2）。宿主容器事实与官方表单度量见
  [官方机制参照](../reference/官方机制参照.md) 的「UI 插件契约」。
- **简单卡片用共享草稿 hook**：只有少量字段的卡片直接用
  `useNamespaceDraft({scope, api, from, patch, saveFailedLabel})` 取
  `{draft, dirty, saving, status, disabled, edit, reset, save}`，不必重写播种/脏判定/
  revision fencing；`from`/`patch` 传模块级稳定函数（参与 hook 依赖比较），数值字段
  以文本承载、越界即 `invalid` 并禁用保存（不静默改写用户输入）。纯校验逻辑放
  `src/client/draft.ts`（不含 JSX），node --test 可直接测。
- **可配置项必须有落点**：schema 里 `.volatile()` 的字段会进入 settings describe
  视图，等于对用户承诺可配。要么在卡片里给出编辑器，要么在卡片内写明「为何不提供
  编辑器、改在哪里配」（如 `role('secret')` 只允许行级注入、批量数据走插件数据目录、
  仅重启生效项、表单未覆盖的字段走「其余字段（JSON）」往返编辑器）——不要留下无 UI
  也无说明的字段。不标 `.volatile()` 的行级 config 属于**部署方平面**：
  GUI 不提供配置入口（插件页只对注册了 `plugins.row.config` 的行显示「配置」），
  由 `cordis.patch.yml` 覆盖，适用于运维旋钮（超时、重试、路径等）——需要让用户改的
  参数就别留在这一层。
- mock_llm.py 脚本条目支持 `{"match", "tool_calls"}` 与 `{"match", "error":{status,...}}`，
  可脚本化复现「模型调工具」「模型请求失败」两类场景。

### 双平面插件开关（经验沉淀）

> 参考实现 `packages/feature-toggle` 已退役（原因见
> [官方版本变更记录](../reference/官方版本变更记录.md)）；以下为仍可复用的机制要点：

- dsh 的插件行分两个平面，开关手段不同：
  - **host 平面**（组合树行）：profile 用户 patch 层（`cordis.patch.yml`）追加
    `{id, disabled: true}` 覆盖即可；dsh 的 `watchUserPatches` 会热应用文件改动
    （HMR config watch → include entry.update），**无需重启**。
  - **preset 平面**（agent 预设声明）：预设 = 组合声明行（官方 preset registry
    的 `@deepseek-ai/dsh-agent-preset` 包装行经
    `agentPresets.register()` 注册），`.agent-presets/` 目录已无读取方——
    新增/覆写 = bundle patch 插入该行（或经插件注册，参考实现
    `packages/agent-preset-chat`），默认预设 = `agent-preset-registry` 行
    config 的 `default`/`selectedDefault`；声明更新即退役旧 revision，新会话
    走新组合，已加入会话保持原组合，**同样无需重启**。
- 封闭目录 + 默认拒绝：开关目标行集合必须是编译期常量（`catalog.ts`），写入口
  统一校验 id ∈ 集合，核心行（api-proxy 硬依赖的 `subagents` 注册表、llm/session/
  settings/webserver 等）根本不进集合——「不可关闭」是机制而非约定。
- 多写入者协调：同形 `{id, disabled}` 条目靠注释标记区分归属（lifeboat 隔离条目
  与管理条目并存时只动自己的）；被 lifeboat 隔离的插件拒绝启用（读其 settings ns
  journal，零依赖）。
- 写入纪律：先备份（`.bak`）→ 校验 → tmp+rename 原子落盘；写入后开健康监视窗口
  （fiber FAILED 监听 + `agentPresets.list()` broken 复核），异常恢复备份热回滚。

## 调试方法（零费用）

1. 类型检查：`dshctl typecheck [包...]`（逐包 `tsc --noEmit`）——消费官方客户端契约
   （`commandUi.register`、`slots.register` 等）时**必须先过这一步**：tsdown 不做类型校验，
   契约漂移只会在浏览器里以运行时异常暴露。
2. 单元测试：`dshctl test`（biome + typecheck + 构建 + node:test + python unittest，禁网络）。
3. 开发实例：`dshctl dev up` → http://127.0.0.1:3082 ，模型全部命中本机 mock
   （`~/.dsh-dev/run/mock-llm.log` 可见每次请求）。
4. 脚本化模型行为：`dshctl smoke` 演示了完整做法——向 `~/.dsh-dev/run/mock-script.jsonl`
   写入带 `match`（请求体子串）的响应条目，mock 按内容命中后消费（可模拟 tool_call 再终答，
   且不受会话标题等辅助请求干扰）。
5. 造会话数据：`dshctl dev seed` 经 headless 真实管线在 `~/.dsh-dev` 生成带 `[seed]` 标记的
   会话（短问答/markdown/代码块/工具调用/长滚动），归入 seed-workspace 专属分组；
   `dev seed --reset` 清空后重造。只写 dev home，严禁指向生产。
6. 无头调试：`dshctl hl <任务> [--tool 名 --args JSON --then 终答]`——不经 web 实例，
   headless profile + mock 跑一轮，终答直接打终端；排障用 `dshctl dev logs mock-llm`。
7. 截图/浏览器交互：`dshctl pw open` 后 `dshctl pw run -- <playwright-cli 命令>`——
   如 `pw run -- screenshot --filename output/playwright/x.png [--full-page]`、
   `pw run -- resize 390 844`（切视口）、`pw run -- snapshot`（取元素 ref）。
8. 组合树预览：`DSH_HOME=~/.dsh-dev dsh --profile web --dump-config` 确认插件行已 insert。
9. 生产布局回归：`dshctl smoke-prod [--linker hoisted|isolated]`——scratch home +
   真实 tgz 安装 + mock LLM + 内置 bash 工具调用，复现生产解析拓扑（不碰生产 home），
   验证平台依赖 peer 化在两种布局下都免疫顶层遮蔽。改依赖声明或 dsh rc 升级后必跑。
10. 服务端日志：`dshctl dev logs`；改代码后 `dshctl dev restart`
    （UI 插件的浏览器半支持 HMR，node 半需重启 dev 实例）。

## 红线

- 开发/测试严禁真实 API 调用：dev home 的 settings.yaml 只指向 mock；`dev up` 会把
  真实密钥环境变量覆盖为 dummy；单元测试禁网络。
- 严禁在 dev 流程中触碰 `~/.dsh`（生产 home）、systemctl 服务、tailscale serve。
